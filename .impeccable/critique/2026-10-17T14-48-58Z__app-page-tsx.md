## Design Specificity Verdict

Signal feels more authored than a generic job board: the quiet briefing rhythm, ranked lead role, saved/later queues, and referral-focused language support the actual morning workflow. The strongest product-specific idea is the decision layer over a feed, not simply another jobs list.

The weak point is that the dashboard’s top controls do not yet tell one clear story. Today, Saved, Later, five filters, the dormant Outreach desk, Refresh, theme, and profile menu all appear before the user has clearly acted on the lead role. The surface therefore becomes more like a competent dashboard template at exactly the moment it should feel like a focused morning brief.

The deterministic scan returned zero findings for `app/`. No false positives were found. Browser automation was not exposed in this session, so no live visual overlay or viewport inspection was possible.

## Overall Impression

The core is calm, credible, and much closer to a real daily tool than a demo. The biggest opportunity is to make each morning feel like one obvious sequence: assess the lead, take the next action, then move through the remaining roles—without having to decode the product’s supporting queues and future capabilities.

## What’s Working

- The lead role earns its priority. Role, company, fit rationale, facts, referral message, and actions are co-located, so the user does not need to jump between tabs to decide.
- Saved and Later acknowledge real job-search behaviour. “Snoozed roles return to Today tomorrow morning” turns an ambiguous defer action into a predictable commitment.
- Account separation and live-feed loading are now legible. The empty workspace and skeleton state avoid showing another account’s sample content as if it were real data.

## Priority Issues

### [P1] The top of the queue asks the user to parse too many modes before they can act

**Why it matters:** A morning review should start with one question—“Is this role worth acting on?” Instead, the user sees three queue destinations, five filters, a future-facing outreach feature, refresh, theme, and account controls before the first job decision. This weakens the “Less noise” promise.

**Fix:** Keep Today as the obvious default. Move Saved and Later into one “Queues” disclosure or give them a quieter secondary position below the list header. Collapse Tier A/B/Applied/Referred into one filter control with a clear “All roles” default. Preserve the visible count but reduce simultaneous decisions to four or fewer.

**Suggested command:** `$impeccable distill`

### [P1] Outreach is visible but does not yet explain its readiness model

**Why it matters:** “Run outreach to unlock” tells the user that something is missing, but not what must be run, where it runs, what appears afterward, or why the job queue already works. This reads as a disabled feature rather than intentional progressive rollout.

**Fix:** Keep it greyed out as requested, but change its supporting line to “No drafts yet — run the optional outreach workflow in your pipeline.” Make the info popover state the result: “When your pipeline publishes contact drafts, this becomes your review desk.” Add one non-primary “How it works” link to the guide or setup screen.

**Suggested command:** `$impeccable clarify`

### [P2] Status language has a trust gap between local action and persistent account progress

**Why it matters:** The account dashboard persists progress, but several toasts still say “on this device.” That language makes a signed-in user question whether Saved, Snooze, Apply, and Referred will survive another device or session.

**Fix:** Base confirmation copy on `progressScope`: say “Saved to your account,” “Marked applied,” and “Snoozed until tomorrow” when Supabase sync is ready; reserve “on this device” for guest mode only. Make one sync state visible only if a save fails.

**Suggested command:** `$impeccable clarify`

### [P2] The profile menu improves scanning, but is too quiet for first-time discovery

**Why it matters:** A silhouette has a familiar meaning, but a user who has just signed in may not know where to confirm which Google account is active. This is especially important because workspaces are private by account.

**Fix:** Keep the icon-only control, but use a first-session hint or a compact tooltip, “Account: name@gmail.com,” on hover/focus. In the menu, retain the full email and add “Private workspace” as the contextual line—not just “Signed in as.”

**Suggested command:** `$impeccable onboard`

### [P3] The queue’s visual rhythm still leans on a standard dashboard pattern

**Why it matters:** The lead is distinct, but below it the rank-plus-six-column table row pattern could belong to almost any job tracker. On a daily tool, that density risks becoming skimmed rather than decided.

**Fix:** Let the first two row facts answer the decision faster: role/company, freshness, then one compact match signal. Put salary and experience into expanded content on narrower screens. Reserve rank numbers for Tier A or when a visible score genuinely explains priority.

**Suggested command:** `$impeccable layout`

## Persona Red Flags

### Alex — impatient power user

- Alex cannot quickly filter to a saved/later state and return via keyboard shortcuts; repeated daily triage remains row-by-row.
- Applying, referring, saving, and snoozing are handled one role at a time with no batch affordance once the user has scanned several credible Tier B roles.
- The account menu is concise, but the separate Refresh action lacks a last-refreshed/working status next to it when Alex needs to verify the feed is current.

### Jordan — first-time job seeker

- Jordan can see “Tier A,” “Tier B,” and “Outreach desk,” but the explanation is hidden behind small info controls. The labels alone assume the user knows Signal’s model.
- “Saved” and “Later” are close but emotionally different concepts; the labels need an always-on one-line distinction at first encounter.
- A dormant Outreach desk looks available because it occupies a strong, bordered tab-like space. Jordan may click it, get a disabled control, and not know the next step.

### Sam — keyboard and screen-reader user

- The profile menu has an accessible name, but it should expose expanded/collapsed state and a more meaningful name such as “Account menu for [email].” Native `details` covers state, but the account identity is hidden until activation.
- The icon-only theme toggle has a label, which is good; the compact info buttons need their tooltip content to be reliably available on keyboard focus (the current CSS approach suggests it is, but live assistive-tech verification is still needed).
- The dense row/expand control must be checked at 200% zoom; the six-column desktop grid can become difficult to navigate or comprehend when wrapped.

## Minor Observations

- The static date can undermine trust once the dashboard is opened on another day; derive it from the actual current/local date or feed run metadata.
- “Worth a referral” is persuasive but not necessarily equal to Tier A; use the same label everywhere or make the distinction explicit.
- Refresh is helpful, but its placement gives it stronger weight than the account menu and competes with the daily queue.
- The guide should be reachable from the account menu or a lightweight help link once the user is inside the dashboard—not only through empty/error paths.

## Questions to Consider

- If a user had only 90 seconds each morning, what should be visible before the first scroll—and what earns a place after it?
- Is “Outreach” a destination users should anticipate every morning, or an occasional workflow that should appear only once drafts exist?
- Should Saved and Later be navigation destinations, or simply outcomes that help the Today queue stay focused?
